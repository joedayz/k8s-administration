Módulo 08 · 6h

Troubleshooting

Diagnóstico de pods, servicios, nodos y control plane en k3s. kubeadm y OpenShift quedan como referencia.

👤 Rol del administrador

El troubleshooting representa el 30% del examen CKA y es la habilidad más valorada en producción:

  • Diagnosticar y resolver problemas de pods en segundos bajo presión
  • Identificar fallos del control plane cuando el cluster no responde
  • Debuggear problemas de red entre servicios y namespaces
  • Reconstruir un cluster parcialmente roto

📘 Teoría

Metodología de troubleshooting (en orden)

¿El problema es de pod, nodo, red o control plane?
        │
        ├── POD: kubectl describe pod → kubectl logs → kubectl exec
        ├── NODO: kubectl describe node → journalctl -u k3s-agent (worker) o -u k3s (server)
        ├── RED: kubectl get endpoints → nslookup desde pod
        └── CONTROL PLANE: systemctl status k3s → journalctl -u k3s
                           kube-system solo tiene CoreDNS, Traefik y metrics-server

En kubeadm la unidad del nodo es kubelet y el control plane son static pods en kube-system. En OpenShift se mira oc get clusteroperators y el kubelet desde oc debug node/<nodo> seguido de chroot /host.

Los 6 estados problemáticos de un pod

EstadoCausa más comúnDiagnóstico
PendingSin nodos disponibles, falta de recursoskubectl describe pod → Events
ImagePullBackOffImagen no existe, credenciales incorrectaskubectl describe pod → Events
CrashLoopBackOffAplicación falla al arrancar, error de configkubectl logs --previous
OOMKilledSupera el límite de memoria (exit 137)kubectl describe pod → Last State
Terminating (atascado)Finalizer pendiente, nodo caídokubectl patch para forzar
Error / RunContainerErrorError en entrypoint, permisoskubectl describe + kubectl logs

Troubleshooting de servicios: el patrón más frecuente

Síntoma: "mi app no llega al servicio"
Diagnóstico:
  1. kubectl get endpoints     → ¿hay IPs? Si no: selector incorrecto
  2. kubectl get pods -l  → ¿los pods están Running?
  3. nslookup ..svc.cluster.local → ¿el DNS resuelve?
  4. curl desde otro pod             → ¿el puerto es correcto?

Troubleshooting de nodos

# Nodo NotReady — siempre empezar aquí:
kubectl describe node      # Conditions, Events, Taints
journalctl -u k3s-agent -n 50    # worker. En el server: journalctl -u k3s

# Causas comunes:
# - k3s-agent parado (systemctl status k3s-agent)
# - Disco lleno (df -h) → DiskPressure=True
# - Certificado caducado (k3s certificate check en el server)
# - El worker no llega al API

kubeadm: journalctl -u kubelet y crictl ps para los static pods. OpenShift: oc debug node/<nodo>, chroot /host, journalctl -u kubelet.
